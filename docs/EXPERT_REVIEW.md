## Why a panel, and why these rules

A single reviewer converges on their own blind spots. Fifteen reviewers with disjoint mandates, no shared context and a requirement to prove each claim from the source produce something a single pass cannot: disagreement. Where two independent reviewers land on the same defect, the signal is strong; where one is alone, it is a hypothesis. The rules were deliberately hostile to flattery:

- **Evidence or it does not exist.** A finding without a file reference and a quoted fact was not to be filed.
- **Docs are claims, not evidence.** Reviewers were told to verify README/SECURITY/spec assertions against code, and to treat a false documentation claim as a finding in its own right.
- **Calibrated scale.** 90+ means it would pass a demanding professional review; 60–74 means competent with material weaknesses; below 40 means broken or misleading.
- **Read-only.** No reviewer could modify the code it judged.

## Reviews by dimension

### Business viability — 56/100

*Business Viability & Value Proposition · weight 7 · confidence high*

> The provisioning-automation half of the pitch is real and the per-order margin math is genuinely tracked, but the money model only works for month one — there is no renewal/recurring charge anywhere in the code, real-mode usage returns an empty array so the entire wallet/usage/credit-policy value proposition is inert in production, and usage debits carry zero markup, so the recurring revenue a reseller business actually lives on is not implemented.

Earned points: the value proposition is real and code-backed for provisioning (CDN fully automated, documented endpoints only, no invented APIs), unit economics are genuinely representable end-to-end — base cost -> markup rule -> customer price -> margin persisted per order and aggregated on the dashboard with demo rows excluded — and time-to-value via the 7-step wizard is short and honest. Lost points, heavily, on the money model: no renewal or recurring charge exists in the schema, jobs or roadmap, so a business selling monthly packages collects revenue once while upstream cost accrues forever (critical); `RealProvider::usage()` returns `[]`, making the entire wallet/usage/credit-policy third of the feature set inert in production; and where usage does flow it is debited at raw cost with no markup, so the metered path earns nothing. Further deductions for real-mode plans being unsellable until flavor ids are hand-entered while the wizard reports pricing complete, for margin being a modelled figure with no reconciliation against actual upstream spend, and for lifetime-only reporting with no MRR. This is competent commercial plumbing sitting under a revenue engine that has not been built — 56 places it just below 'competent with material weaknesses a reviewer would insist on', because the weakness is the business model itself rather than an implementation detail.

**What holds up**

- Unit economics are first-class in the data model, not an afterthought: `PricingEngine::quote()` (src/Pricing/PricingEngine.php:61-72) returns `base_cost`, `markup_percent`, `markup_source`, `margin` as one immutable snapshot, `OrderService::create()` persists `amount`/`base_cost`/`margin` as dedicated indexed columns (src/Orders/OrderService.php:105-107, src/Install/Schema.php:56-58), and the admin dashboard aggregates all three (src/Admin/Menu.php:86-88). Margin is reportable per order and in aggregate — most hackathon builds stop at 'price = cost * markup'.
- Demo revenue is excluded from real financials: `$demo_filter = Plugin::demo_mode() ? '' : ' AND is_demo = 0'` (src/Admin/Menu.php:85) means seeded demo orders can never inflate the reseller's reported revenue/margin once they go live. That is a commercially serious detail most demos get wrong.
- Real price discrimination exists and is enforced server-side: rule resolution customer -> product -> global with stacked discount and fixed adjustment (src/Pricing/PricingEngine.php:35-59), plus a per-customer `spending_limit` gate at checkout (src/Orders/OrderService.php:88-94). A reseller can actually run tiered/agency pricing and cap risky accounts on day one.
- Time-to-value is short and the wizard is honest about the demo/real split: 7 steps ending in page creation, with `Options::set('demo_mode', false)` only after a live `test_connection()` succeeds (src/Onboarding/Wizard.php:196-206). A reseller with a valid Arvan machine-user key can have a branded storefront published in one sitting with no WooCommerce, no builder, no Node.
- The limitation documentation is unusually honest and matches the code: docs/API_INTEGRATION.md:52-61 lists the absent billing/pricing/sub-account APIs and names the exact shipped fallback for each, and `RealProvider::usage()` returning `[]` (src/Arvan/RealProvider.php:317-320) is the truthful implementation of that admission rather than a fake.

**Findings**

- `EX-004` 🔴 critical **No renewal or recurring billing anywhere — a 'monthly package' is charged exactly once, forever** — `src/Install/Schema.php:84-103, src/Jobs/JobRunner.php:111-118`  
  The reseller sells a monthly package (BaseCosts seeds are explicitly 'monthly base costs', BaseCosts.php:56-75) and collects one payment. ArvanCloud keeps charging the reseller's upstream account hourly forever. Month 2 onward every active service is pure loss at 100% of upstream cost. At the documented Stage A profile (2,000 services, CAPACITY_MODEL.md:9-11) the reseller's upstream bill compounds monthly against a one-time revenue event. This is not a feature gap, it is the business model's revenue engine missing.
- `EX-005` 🔴 critical **The entire wallet/usage/credit-policy subsystem is dead code in real mode** — `src/Arvan/RealProvider.php:317-320`  
  In production a customer's `available` balance can only ever be >= 0, so `PolicyEngine::stage()` returns HEALTHY permanently and the warning/critical/grace/restricted ladder, the negative-balance dashboard panel (templates/admin/dashboard.php:31-45), the reconciliation view and the usage tab never fire. Four of the eleven tables and roughly a third of the advertised feature surface ('Usage', 'Wallet', 'Policies' rows in the README capability table) do nothing for a paying reseller. README.md:211 admits usage 'is not fetchable' but does not state that the credit-policy product therefore has no real-mode function.
- `EX-031` 🟠 high **Usage debits are posted at raw upstream cost — the metered revenue path earns zero margin** — `src/Usage/UsageSync.php:116,123`  
  On the consumption model the plugin is architecturally built for, the reseller resells at exactly cost: 0% gross margin, and `orders.margin` does not capture it either because no order row is created. The demo therefore shows a customer's wallet being drained by the full upstream monthly cost on top of a marked-up package payment already collected at checkout — the customer is charged roughly twice for the same resource while the reseller's books record margin only once. The money model is not internally consistent between its two halves.
- `EX-032` 🟠 high **Real-mode cloud-server plans are unsellable out of the box; the wizard reports pricing as complete anyway** — `src/Pricing/BaseCosts.php:59-64 vs src/Arvan/RealProvider.php:66-77`  
  A real reseller finishes onboarding, is told «راه‌اندازی کامل شد. فروشگاه شما آماده است!» (Wizard.php:224), and lands on an empty cloud-server page. Recovery is hand-transcribing every Arvan flavor id and its price into the one-row-at-a-time form at templates/admin/pricing.php:52-58. Time-to-first-sale goes from minutes to an hour of error-prone data entry, and a mistyped base cost silently mis-prices every future order since margin is derived from it.
- `EX-033` 🟠 high **Reported margin is notional — nothing reconciles it against what the reseller actually owes ArvanCloud** — `src/Admin/Menu.php:86-88, src/Pricing/BaseCosts.php:31-40`  
  The 'سود ناخالص' figure on the dashboard is a modelled number, not a P&L. If Arvan's real prices drift, a promotion applies, or a server runs 45 days instead of 30, the dashboard keeps reporting healthy margin while the reseller is losing money. A reseller cannot use this to decide markup levels, which is the single most important decision the tool exists to support.
- `EX-090` 🟡 medium **Financial reporting is lifetime-cumulative only — no MRR, no period, no churn** — `src/Admin/Menu.php:86-89`  
  For a recurring-revenue business the operator cannot answer 'what did I earn this month', 'is revenue growing', or 'how many services churned'. Combined with the missing renewal engine, the reseller has no instrument that would even reveal the month-2 revenue cliff. ROADMAP.md:16 mentions CSV export and monthly statements only at v1.2.
- `EX-091` 🟡 medium **Two of three products still require manual reseller intervention to deliver credentials** — `src/Arvan/RealProvider.php:220-225, docs/API_INTEGRATION.md:59`  
  README.md:13-15 sells the removal of exactly this — 'copy the IP and password, and email it back'. In practice the reseller still logs into the panel per cloud-server sale to retrieve or reset the root password, and per object-storage sale to mint and hand over S3 keys. The 'no human in the loop' claim holds fully only for CDN. The object-storage caveat is disclosed in README's limitations; the cloud-server password gap is not.

**Opportunities**

- The margin snapshot on every order (`orders.pricing` JSON + `margin` column) is the right substrate for a real reseller P&L — per-product margin mix, price-elasticity views and a 'which plans actually make money' report are query-only work on data already being written.
- `Customers\Rules` already carries per-customer markup, discount, spending_limit and grace_days, which is a B2B/agency-reseller tier waiting to be packaged and priced (e.g. wholesale accounts with negotiated markup) — a commercially stronger position than competing on retail price alone.
- The `ProviderInterface`/`PaymentProviderInterface` boundary means the same storefront could resell a second Iranian cloud provider with one adapter — a genuine multi-vendor play that no ArvanCloud-panel-based competitor can match, and a better long-run moat than the provisioning automation itself.
- `Ledger` already defines `reservation`/`release` types (Ledger.php:17) that nothing currently emits; wallet-first checkout (ROADMAP v1.2) would turn the wallet from a decorative balance into the prepaid-credit product Iranian hosting buyers actually expect, and it is the natural funding mechanism for the missing renewal charge.

### Code quality — 84/100

*Code Quality & Maintainability · weight 8 · confidence high*

> Unusually disciplined for a hackathon build — small single-purpose classes, consistent WordPress conventions, genuinely explanatory WHY comments, verified PHP 7.4 syntax discipline, and pure domain classes (PricingEngine, StateMachine, PolicyEngine, Ledger::derive) that are unit-tested without a DB — held back by a fragile string-matching contract between the job runner and the provisioner, ~100 lines of dead provider/helper surface, a default value that disagrees with itself across six files, and zero automated coverage of any `$wpdb` path.

The codebase earns high marks on the fundamentals that actually decide maintenance cost: consistent conventions across 42 PHP files, no class over ~340 lines, pure-domain separation that makes the money math testable, whitelist-based input handling applied uniformly, verified PHP 7.4 syntax discipline, and comments that explain non-obvious decisions (portable duplicate detection, admin_init redirect hazard, refund-before-transition ordering) rather than restating code. Points come off for concrete, provable defects rather than style: a control-flow contract built on substring-matching prose that mis-handles Persian error messages (JobRunner.php:114), a self-contradicting default value spread across six files, ~100 lines of provider/helper code with no callers, a dead branch that silently defeats its own documented credential-selection rule, and a test suite that by construction cannot cover a single `$wpdb` path — leaving the ledger and idempotency code, the riskiest in the repo, without a regression net. None of these are architectural; all are the kind of thing a demanding reviewer would insist on before merge, which places it solidly in the strong-but-not-production-clean band.

**What holds up**

- Domain logic is deliberately separated from WordPress so it is testable: `src/Pricing/PricingEngine.php`, `src/Orders/StateMachine.php`, `src/Policies/PolicyEngine.php` and `Ledger::derive()` carry no `defined('ABSPATH')` guard and no `$wpdb`, and `tests/unit/` exercises all four directly (46 test methods, matching the README's claim exactly).
- Comments explain WHY, not WHAT, and the non-obvious ones are the load-bearing ones: `src/Wallet/Ledger.php:69-77` explains that `rows_affected` (not `insert_id`) is the portable duplicate signal on both MySQL and the SQLite layer, and `src/Identity/Customers.php:38-42` explains why `admin_init` must not blanket-redirect (it would swallow admin-post.php form submissions).
- Single-writer discipline is real and enforced in code, not just documented: `OrderService::transition()` (src/Orders/OrderService.php:141) is the only status writer and does an optimistic `UPDATE … WHERE id = %d AND status = %s`, returning false when another writer won; `claim_paid()` (:161) folds the payable-state and amount check into one UPDATE.
- Input handling is uniformly whitelist-based rather than ad-hoc: `Options::set()` (src/Support/Options.php:55) silently drops keys absent from `DEFAULTS`, `OrderService::sanitize_config()` (:34) whitelists per-product fields, and `Rules::save()`/`Credentials::save()` intersect against known product keys — the same pattern applied consistently in every write path.
- PHP 7.4 compatibility is actually disciplined, not merely declared: a repo-wide search for `?->`, `match(`, `str_contains`, promoted properties, enums and attributes returns zero hits in `src/`, and DTOs in `src/Arvan/DTO.php` use explicit untyped public properties rather than 7.4-incompatible constructs.

**Findings**

- `EX-023` 🟠 high **Job runner decides retry-vs-success by substring-matching English prose from Provisioner** — `src/Jobs/JobRunner.php:114`  
  Two failure modes. (1) Rewording either Provisioner string — a natural refactor, they are untranslated debug prose — silently converts a benign 'already handled' result into a thrown exception, so the job retries 5 times and lands in `dead` with an admin alert. (2) Non-retryable ProviderError kinds (`auth`, `invalid`) return `$e->customer_message()`, a Persian string (src/Arvan/DTO.php:88) that can never match either English needle, so a permanently misconfigured credential burns all 5 attempts and 53 minutes of backoff before surfacing.
- `EX-075` 🟡 medium **Default brand color is defined six times with two different values** — `src/Support/Options.php:28`  
  A fresh install renders with `#14bfb4` (from DEFAULTS) but the moment an admin saves branding with an empty or invalid color, `sanitize_hex_color(...) ?: '#0c6960'` writes the *other* teal — the storefront accent silently changes on an unrelated save. Changing the product's default color now requires editing six files and noticing that two of them disagree.
- `EX-076` 🟡 medium **~100 lines of dead provider and helper surface that must still be maintained and reviewed** — `src/Arvan/ProviderInterface.php:36`  
  Every future contributor reads, reviews and must keep compiling ArvanCloud delete/status endpoints that no code path can reach — including a `DELETE /servers/{id}` implementation that has never executed. New provider adapters are forced to implement three methods nothing calls. The duplicated masking means a change to the mask format silently applies in one place only.
- `EX-077` 🟡 medium **Credential selection has a redundant branch that defeats its own stated preference** — `src/Arvan/Credentials.php:115`  
  The second `if` fires on exactly the rows the first one skipped, so the pair collapses to `if ($fallback === null) $fallback = $candidate;` — the documented preference for an unrestricted credential is never applied. A reseller with credential A restricted to `cdn` (priority 5) and credential B unrestricted (priority 10) gets A as the fallback for `object_storage`, contradicting the class docblock's stated selection order. The dead branch also actively misleads the next reader into believing the preference exists.
- `EX-078` 🟡 medium **No automated test covers any `$wpdb` path — the money and idempotency code has no regression net** — `tests/bootstrap.php:79`  
  The subtlest code in the repo is the untested code. `Ledger::append`'s replay-vs-real-failure distinction (Ledger.php:66-79) is exactly the logic whose regression means silent money loss, and a refactor of it produces a green `composer test`. New contributors get no fast feedback on the paths CONTRIBUTING.md declares highest-risk.
- `EX-079` 🟡 medium **Blocking sleeps inside the synchronous checkout/callback request path** — `src/Arvan/RealProvider.php:201`  
  A real-mode server purchase can hold the payment-callback PHP worker for 15 s of polling plus up to ~5.5 s of client retry — past many PHP `max_execution_time` and gateway callback timeouts, in which case the customer sees a failure for an order that actually succeeded. It also makes the provisioning path effectively impossible to unit-test without waiting real seconds.
- `EX-080` 🟡 medium **Adding a product means editing ~10 sites, including hard-coded product lists that bypass Catalog::PRODUCTS** — `src/Arvan/Credentials.php:36`  
  The two literal arrays are the dangerous ones: a fourth product added to `Catalog::PRODUCTS` would be sellable and priceable, yet silently unassignable to a credential and silently strippable from a customer's `allowed_products` — a permission bug with no error message. The remaining spread makes 'add a product' a multi-hour change with no checklist in code.
- `EX-127` ⚪ low **Three concrete comment defects: a docblock attached to the wrong function, a stale @return, and a duplicated const comment** — `src/Payments/PaymentService.php:22`  
  IDE hovers and generated API docs attach a callback signature to a boolean predicate; a reader of `guard()` looks for a return value that does not exist. These are cheap credibility losses in a codebase whose comments are otherwise its strongest asset.
- `EX-128` ⚪ low **UsageSync::apply_policy is an 80-line multi-responsibility function with a duplicated `global $wpdb`** — `src/Usage/UsageSync.php:130`

Highest-risk function in the module and, per the finding above, entirely untested.
- `EX-129` ⚪ low **Admin order action relies on a helper's hidden exit() for control flow, with no return statements** — `src/Admin/Actions.php:243`

### Architecture — 77/100

*Technical Architecture & Engineering Quality · weight 10 · confidence high*

> A genuinely well-reasoned modular monolith with real domain purity, a real provider seam and unusually disciplined DB-level concurrency correctness — undercut by a service-locator composition root that every module reaches back into (creating the cycles the docs deny), two layer inversions, and unrecoverable stuck states in the "durable" job/provisioning path.

The fundamentals a demanding reviewer cares about are genuinely present and verified in code, not just claimed: four truly WordPress-free domain cores, a provider interface with two real implementations, and a consistent, well-reasoned strategy of pushing concurrency correctness into unique keys and single-row optimistic claims (including the non-obvious rows_affected-vs-insert_id and replay-vs-DB-error distinctions). That earns high-70s. Points come off for architectural discipline that the documentation overstates: the composition root is a service locator that seven modules import, producing Plugin-Arvan and Plugin-Payments cycles against an explicit \"no circular dependencies\" claim; Jobs inverts the declared layer direction; and the admin layer runs raw SQL against another module's table to decrypt a secret. The two findings that keep it out of the 80s are runtime, not stylistic: the \"durable\" queue has no stale-claim reaper and the provisioning path has an unrecoverable stuck state that the runner reports as success, both on the paid-order path. Scored 77 — strong engineering with a handful of gaps a reviewer would insist on before production.

**What holds up**

- The pure domain cores are genuinely pure, not aspirationally pure: `Pricing/PricingEngine.php`, `Orders/StateMachine.php` and `Policies/PolicyEngine.php` contain zero WordPress calls, zero `$wpdb`, no `defined('ABSPATH')` coupling in the two engines, and are static-function-only — they unit-test directly (tests/unit/{PricingEngine,StateMachine,PolicyEngine}Test.php). `Ledger::derive` (Wallet/Ledger.php:91-120) is likewise a pure fold over rows with the DB read isolated in `balance()`.
- `Arvan\ProviderInterface` is a real seam, not theatre: `DemoProvider` (180 lines) implements all seven methods with the same DTOs, deterministic per-(resource,hour) usage generation so ingestion dedup is provable, and a scripted failure trigger (`DemoProvider.php:80-87`) that exercises the provision_failed→retry→active path. Two live implementations behind one contract is the definition of a load-bearing abstraction.
- Concurrency correctness is consistently delegated to the database rather than to hopeful application code, and the reasoning is right: `orders.payment_ref UNIQUE` + a single amount-bound `UPDATE ... WHERE status IN (payable)` (OrderService.php:179-183), `services.order_id UNIQUE`, `ledger UNIQUE(ref_type,ref_id,type)`, `usage UNIQUE(service,period_start,period_end)`, and jobs claimed by `UPDATE ... - Ledger/Services use `rows_affected` rather than `insert_id` as the duplicate signal and explicitly separate an ignored duplicate from a real DB failure (Wallet/Ledger.php:59-71) — a subtlety most codebases get wrong and silently lose money on.

**Findings**

- `EX-008` 🟠 high **Durable job queue has no reaper: a crashed worker strands a job in 'running' forever** — `src/Jobs/JobRunner.php:56, 73-77`

For `provision_order` that means a paid order silently never provisions — the exact failure ADR-0004 claims the table design eliminates ("crash-safety of paid-but-unprovisioned orders").
- `EX-009` 🟠 high **Orders can become permanently stuck in 'provisioning' with an orphaned upstream resource** — `src/Provisioning/Provisioner.php:44-48, src/Jobs/JobRunner.php:112-116`  
  A single crash or timeout in the provisioning window produces: a paid customer with no service, an order frozen in a non-terminal state, a real ArvanCloud resource created and billed with no local `services` row (so it is invisible to usage sync and to `Ledger::reconciliation_by_credential`), and a job queue that reports success. No code path recovers it; the admin "retry" button hits the same not-claimable branch.
- `EX-010` 🟠 high **Up to 15s of blocking sleep plus synchronous email inside the payment callback request** — `src/Arvan/RealProvider.php:200-218, src/Payments/PaymentService.php:91-97`  
  The payment callback — the one request that must return fast and idempotently — can block for 15-25s plus SMTP. Real gateways retry on callback timeout; the replay path is safe, but the customer-visible request stalls. Worse, this directly defeats ADR-0004's stated mitigation of its own named risk ("Long-running jobs vs PHP max_execution_time. Batch size 5 keeps runs short"): five queued `provision_order` jobs at ~15s+HTTP each blow past a 30s `max_execution_time`, and the killed run leaves rows in the un-reapable `running` state above.
- `EX-054` 🟡 medium **Composition root is a service locator that seven modules depend on, creating the cycles ARCHITECTURE.md denies** — `src/Plugin.php:60-82 (consumers: Wallet/Ledger.php:47, Arvan/Catalog.php:42,50,60,66, Orders/OrderService.php:110, Provisioning/Provisioner.php:52,55, Usage/UsageSync.php:51, Payments/PaymentService.php:35,58,114, Admin/Menu.php:85)`  
  Nothing below Presentation can be constructed or tested without the root and its ambient global state (demo mode is re-derived from options + DB at every call site). This is exactly the "static accessors rot into hidden globals" risk ADR-0001 names, and it is why the unit suite covers only the four pure classes plus Crypto/License — `Ledger::append`, `OrderService::create`, `Catalog` and `Provisioner` are structurally untestable without a full WP install.
- `EX-055` 🟡 medium **Presentation layer runs raw SQL against another module's table to fetch an encrypted secret** — `src/Admin/Actions.php:202-204, src/Admin/Menu.php:80-89`  
  Secret handling leaks out of the module that owns it, so any future change to storage/encryption must be chased into the admin layer; and the ownership rule in ARCHITECTURE.md:32-47 (`Arvan` owns credentials, `Orders` owns order rows) is not actually held by the code. It also means `Support\Crypto` decrypt calls appear in a request handler rather than behind the credential API.
- `EX-056` 🟡 medium **Jobs (Infrastructure) hard-codes dispatch into Application modules, inverting the declared layer direction** — `src/Jobs/JobRunner.php:108-124`  
  The queue cannot be extracted or reused without dragging the business modules with it — which undercuts ADR-0011's Stage C claim that `Jobs` is a clean extraction seam ("a worker polls the same table"). Adding a job type requires editing an infrastructure file.
- `EX-057` 🟡 medium **Demo-mode check issues an uncached DB query on every ledger write and catalog read** — `src/Plugin.php:49-57, src/Wallet/Ledger.php:47, src/Usage/UsageSync.php:116-125`  
  A usage sync ingesting N records issues N extra credential queries; `Menu::dashboard()` alone triggers it three times per page load; `Catalog::plans/options` twice per product. Cheap per call, but it puts an unbounded uncached query in the money write path for no functional reason.
- `EX-118` ⚪ low **The documented module dependency table is stale in at least four places** — `ARCHITECTURE.md:32-47`  
  The table is the artifact a reviewer or new engineer trusts to reason about coupling; being wrong on four edges means it cannot be used to predict blast radius, and nothing enforces it.
- `EX-119` ⚪ low **Only one extension point exists in the entire plugin; no lifecycle events at all** — `src/Plugin.php:77 (repo-wide)`  
  For a WordPress plugin handling orders and money, the absence of events like `arvrs_order_paid` / `arvrs_service_provisioned` means no CRM, accounting or analytics integration is possible without forking. The one real seam (payments) is also the only one whose abstraction has a second implementation.
- `EX-120` ⚪ low **The claim that WordPress-freeness is "enforced by the unit suite" is not mechanically true** — `ARCHITECTURE.md:28, tests/bootstrap.php:8-103`  
  The purity property is real today (I verified the three engines call nothing), but it is preserved by discipline, not by the mechanism the doc credits — so it will silently erode.

**Opportunities**

- `PaymentService::start_topup` persists top-up intents as individual `wp_options` rows (`arvrs_topup_<ref>`, PaymentService.php:112) with no expiry or cleanup — the `ponytail:` comment names the ceiling honestly, but abandoned intents accumulate forever and the orders table already models exactly this shape.

### Reliability — 71/100

*Reliability, Failure Handling & Data Integrity · weight 10 · confidence high*

> The idempotency-first design is genuinely well thought out — atomic single-UPDATE claims, an append-only ledger with a unique business key, and a crash back-fill for usage — but it is undermined by a duplicate-remote-resource path on API timeout, two states (order `provisioning`, job `running`) from which no admin repair exists, and a swallowed write on the money path with no reconciliation repair.

The core primitives are genuinely above hackathon grade and earn most of the score: every state claim is a race-free single UPDATE, the ledger is append-only with derived balances and a unique business key, and the duplicate-vs-DB-error distinction in Ledger::append plus the usage back-fill show real understanding of partial-failure semantics. Points come off for four things a reviewer would insist on before production: a concrete duplicate-remote-resource path (POST retried on timeout with the idempotency key ignored, directly contradicting the Provisioner's own docblock), an order state (`provisioning`) with zero admin recovery where the retry job reports success, a job state (`running`) with no reaper and no retry, and a swallowed write on the settled-payment path whose stated safety net (reconciliation) cannot actually detect it. Migration safety adds a further deduction since the whole idempotency model rests on unique indexes that dbDelta may silently fail to create and nothing verifies. That places it at the top of the "competent but with material weaknesses" band rather than in "strong".

**What holds up**

- Ledger idempotency is done correctly and defensively: `INSERT IGNORE` against `UNIQUE KEY uniq_ref (ref_type,ref_id,type)` (Schema.php:119), with `rows_affected` — not `insert_id` — as the duplicate signal, and `$wpdb->last_error` checked so a real DB failure throws instead of being silently reported as a benign replay (Ledger.php:57-71). That distinction is the exact thing most implementations get wrong, and the comment shows they knew why.
- Every state claim is an atomic single-row UPDATE with the prior state in the WHERE clause: `claim_paid` guards on `payment_ref = %s AND amount = %d AND status IN (...)` (OrderService.php:179-183), `transition()` on `WHERE id = %d AND status = %s` (OrderService.php:150-153), and the job claim on `WHERE id = %d AND status = 'pending'` (JobRunner.php:73-78). Racing callback/job/admin writers lose cleanly with no lock and no SELECT-then-UPDATE window.
- UsageSync::ingest back-fills a missing debit: when the period INSERT IGNORE reports 0 rows it re-looks-up the existing usage row and re-runs `Ledger::append` (UsageSync.php:106-119), so a crash between the usage row and its ledger debit self-heals on the next sync instead of losing revenue permanently.
- Refund ordering is correct and reasoned: the wallet credit is appended first and the order is only transitioned to REFUNDED afterwards, so a failed ledger write leaves the order in its prior refundable state rather than REFUNDED-without-credit (Actions.php:282-293).
- The HTTP layer normalizes failure into actionable kinds — separate connect (5s) and read (20s) timeouts, bounded retries, `Retry-After` honored up to 5s then escalated to the job backoff, and auth/invalid/rate_limit/timeout/unavailable classification with correlation IDs (ArvanClient.php:85-133) — and Provisioner rethrows only the retryable kinds so the job runner backs off (Provisioner.php:68-70).

### Data & analytics — 72/100

*Data Model, Analytics & Reporting Quality · weight 7 · confidence high*

> The transactional data model is genuinely well-designed — append-only ledger with derived balances, four distinct races each closed by a purpose-built UNIQUE key, integer money, UTC timestamps, and a clean order→event→service→usage→ledger traceability chain — but the analytics half is thin (lifetime sums with no time dimension, no export) and the `is_demo` dimension stops short of the customer wallet, leaving demo money in real balances.

The transactional core earns a strong mark: 11 purposefully-shaped tables, integer money, UTC/utf8mb4, an append-only ledger with no mutable balance column, and four distinct concurrency races each closed by a matching UNIQUE key with a correct `rows_affected` duplicate signal — that is better than most production WordPress plugins. Points come off for four things a reviewer would insist on: the `is_demo` dimension covers only three admin aggregates and leaves demo money in every customer wallet balance; `negative_since_days` is an approximation that makes the RESTRICTED policy stage unreachable under the hourly sync cadence; `balance()` scans unbounded history in PHP and is called N+1 on the admin customers page; and the analytics themselves are lifetime sums with no date range, no per-product or per-customer breakdown, and no export, which is not enough to run a reseller business on. Secondary deductions for five dead/missing indexes that contradict DATA_MODEL.md, no retention path on four growing tables, and documented model surface (four ledger types, `orders.credential_id`) that no code writes.

**What holds up**

- Idempotency is designed into the keys, not bolted on in application code: `ledger` UNIQUE `(ref_type,ref_id,type)` (Schema.php:119), `usage_records` UNIQUE `(service_id,period_start,period_end)` (Schema.php:136), `services` UNIQUE `order_id` (Schema.php:99) and `orders` UNIQUE `payment_ref` (Schema.php:66) each close a specific double-write race, and Ledger::append uses INSERT IGNORE + `rows_affected` (not `insert_id`) as the duplicate signal — with an explicit `last_error` check so a real DB failure is never silently reported as a benign replay (Ledger.php:63-71).
- Balances are truly derived — there is no mutable balance column anywhere in the 11 tables, and the derivation is a pure function (`Ledger::derive`, Ledger.php:91-120) unit-tested without a DB (tests/unit/LedgerDerivationTest.php).
- Money is integer toman everywhere (`amount`/`base_cost`/`margin`/`cost` all `bigint(20)`), quantity is `decimal(20,4)`, no float touches a money column; timestamps are consistently UTC (`Helpers::now()` = `current_time('mysql', true)`, Helpers.php:73-76) and charset comes from `$wpdb->get_charset_collate()` so Persian text gets utf8mb4.
- End-to-end traceability actually holds: order → `order_events` (every transition appended by the single writer `OrderService::transition`, OrderService.php:144-159) → ledger rows keyed on `payment_ref` → `services.order_id` → `usage_records.service_id` → ledger `('usage', usage_id)` → `audit_log`. A given payment can be walked to its provisioned resource and its debits without guessing.
- Deliberate, correct denormalization: `orders.amount/base_cost/margin` are snapshotted alongside the immutable `pricing` JSON quote, so revenue aggregates are single-table scans rather than re-running the pricing engine over history — and the v3→v4 migration back-stamps `ledger.is_demo = 1` only when the site is still in demo mode (Schema.php:216-227), which is the right call.

### Scalability — 62/100

*Scalability & Performance · weight 8 · confidence high*

> The schema, indexing, atomic job claiming and asset discipline are genuinely well-built, but the single most-executed hot path (wallet balance on every page render) is an unbounded row fetch summed in PHP, the admin customer list N+1s that same call 20 times, and three of the scalability doc's headline claims — including one labelled "[verified in code]" — are contradicted by the code they describe.

Earned points for real schema-level scaling work that most hackathon entries skip: DB-enforced idempotency via unique keys, indexed FK/status/created_at columns, a correct atomic job claim, server-side pagination everywhere, conditional asset enqueue with self-hosted fonts, and a docs set that labels assumptions and names numeric triggers. Lost heavy points because the most-executed path in the product — wallet balance in the shared front-end context — is an unbounded row fetch summed in PHP that the docs describe as an indexed aggregate, the admin customer list multiplies that same call 20×, and the catalog does uncached blocking upstream calls in page render with no negative caching despite a claim marked "[verified in code]". Three contradicted claims (one of them explicitly labelled as verified) plus a stuck-'running' job leak with no reaper are exactly the things a demanding reviewer would insist on before believing the Stage A envelope. Competent, thoughtfully documented, but with material weaknesses on the paths that matter most.

**What holds up**

- Schema is designed for scale, not convenience: every FK/status/created_at is indexed and idempotency is enforced by DB constraints, not app logic — `UNIQUE KEY uniq_ref (ref_type,ref_id,type)` on ledger (src/Install/Schema.php:119), `UNIQUE KEY uniq_period (service_id,period_start,period_end)` on usage_records (:136), `UNIQUE KEY order_id` on services (:99). Retry storms therefore add zero rows instead of amplifying writes.
- Job claiming is correct under concurrency with no PHP-process state: `UPDATE ... SET status='running' ... WHERE id=%d AND status='pending'` and a `$claimed !== 1` bail (src/Jobs/JobRunner.php:73-79). Two runners cannot win the same job, so horizontal PHP scaling needs no coordination layer.
- Asset loading is disciplined: `Front\Assets::maybe_enqueue()` bails unless the singular post actually contains one of the six plugin shortcodes (src/Front/Assets.php:20-32); 27KB CSS + 6KB JS, no build step, self-hosted woff2 with `font-display: swap` (assets/css/front.css:49-51), zero third-party requests.
- Docs separate measurement from assumption honestly and name falsifiable triggers rather than vibes: CAPACITY_MODEL.md labels every row [assumption] vs [measured] (:3, :44-51), and SCALABILITY.md:72-75 gives numeric change-triggers (jobs backlog >500, sync wall-clock >60s, ledger aggregate p95 >100ms). It also self-identifies a first bottleneck (:63) instead of claiming none exists.
- Pagination is real on every list surface: `OrderService::list()` (src/Orders/OrderService.php:216-234), `Services::list()` (src/Services/Services.php:69-82), `Ledger::entries()` (src/Wallet/Ledger.php:156-165) all take page/per_page with LIMIT/OFFSET, and the admin templates render prev/next controls (templates/admin/orders.php:47-48).

**Findings**

- `EX-003` 🔴 critical **Ledger::balance() fetches every ledger row for a customer into PHP, on every front-end page render** — `src/Wallet/Ledger.php:123-133, src/Front/Shortcodes.php:48`  
  CAPACITY_MODEL.md:22 puts ledger growth at 48,000 rows/day across 1,000 customers = ~48 rows/customer/day, so the ≤10³ figure is exceeded in three weeks and a one-year-old customer's every page view loads ~17,500 rows into PHP memory. Nothing about this is an indexed aggregate; it is an O(rows-per-customer) fetch on the most-executed path in the product, and it degrades continuously and permanently because the ledger is append-only with no checkpointing.
- `EX-027` 🟠 high **Admin customer list N+1s the unbounded balance query — 20 full ledger scans per page render** — `src/Admin/Menu.php:170-179`  
  Each iteration is the unbounded fetch from finding #1, so the customers screen loads 20 × (that customer's entire ledger history) into PHP per render — ~350,000 rows at the capacity model's own one-year volumes. The pagination is real but it bounds the wrong axis: rows-per-page is capped, rows-per-row is not. This is the exact pattern the doc claims is fine.
- `EX-028` 🟠 high **Catalog cache miss makes a blocking upstream call inside page render, with no negative caching and no stampede guard** — `src/Arvan/Catalog.php:47-55, src/Arvan/ArvanClient.php:17-19`

During an ArvanCloud degradation it is worse: because errors are never cached, *every* page view retries — up to 3 attempts × 20s + backoff per call, ×2 calls for cloud_server ≈ 120s of blocked PHP-FPM worker per visitor. - `EX-029` 🟠 high **Hourly usage sync rescans the entire ledger twice — the real first bottleneck, and not the one the docs name** — `src/Usage/UsageSync.php:83-85, :131-143, src/Wallet/Ledger.php:136-153`

SCALABILITY.md:63 names "usage ingestion via WP-Cron" as what breaks first and prescribes chunking by service-ID range (:67); chunking does not help here, because the policy pass cost is proportional to accumulated ledger size, not to the batch. The documented fix does not address the documented-away bottleneck's larger sibling.
- `EX-030` 🟠 high **sync_all() is unbounded and unchunked in one request; the demo provider materialises every usage row in memory first** — `src/Usage/UsageSync.php:36-89, src/Services/Services.php:84-95, src/Arvan/DemoProvider.php:146-174`

There is no checkpoint, so a timeout at 90% wastes the run (idempotency makes it safe, not cheap). The docs acknowledge this precisely (:63-67), which is worth real credit — but the shipped code is still the unchunked version, so the Stage A envelope of "≤2,000 active services" is an untested claim about code that provably allocates 96k objects at that number.

SCALABILITY.md:25 names `status='dead'` count as one of the two numbers worth alerting on, so the failure mode that produces no 'dead' row is exactly the one monitoring misses. Probability rises with load, since long-running jobs are the ones that time out.

  `GROUP BY customer_id ORDER BY <computed> ASC` cannot use an index for the sort, so it is a full scan plus temp table plus filesort over ~17.6M rows/year (CAPACITY_MODEL.md:22); the credential reconciliation is a full scan of the 17.5M-row usage table joined to services. `count_users()` is a known full usermeta scan. None of it is cached — grep confirms the only `set_transient`/`wp_cache_*` uses in src/ are the catalog and the rate limiter — so cost is paid per admin page view, and the dashboard is the page an operator refreshes most.
- `EX-088` 🟡 medium **Pricing N+1: one customer_rules query per plan, repeated for every plan on every storefront and product render** — `src/Pricing/Pricing.php:23, src/Customers/Rules.php:21-27, src/Front/Shortcodes.php:72 and :97`  
  The identical single row is re-fetched once per plan: with ~20 plans across three products that is ~60 duplicate queries per storefront render for a logged-in customer, and the catalog REST endpoint repeats it per plan per call. It scales with catalog size rather than customer count, so it will not appear in the doc's customer-count scale table at all — but it is paid on the storefront, the highest-traffic page (CAPACITY_MODEL.md:33 assumes 10 req/s burst there).
- `EX-089` 🟡 medium **Plugin::demo_mode() runs an uncached credentials query per call, including once per ledger row during ingestion** — `src/Plugin.php:50-56, src/Arvan/Credentials.php:125-131, src/Wallet/Ledger.php:47`  
  Doubles the query count of the ledger write path: at the capacity model's 48,000 ledger rows/day that is 48,000 extra round trips per day, concentrated inside the hourly sync request that finding #5 already shows is the tightest one. `Plugin::arvan()` and `Catalog::plans()` call it too, so it also lands on page renders.

  Each customer-dashboard render sorts that customer's whole usage history (~17.5k rows/year) to return 20 — a filesort that grows linearly and is invisible until it isn't. OFFSET pagination re-scans skipped rows, so deep admin pages degrade, and `templates/admin/orders.php:48` infers "has next page" from `count($orders) === 20` rather than a count, so there is no total to bound it with.

- The doc set is 80% of the way to being genuinely trustworthy — it names triggers, separates [measured] from [assumption], and self-identifies a bottleneck. Re-deriving the three contradicted claims (ledger "indexed aggregate", customer list "fine", storefront "no external HTTP [verified in code]") against the code would make the whole handbook load-bearing rather than aspirational.

### Security — 84/100

*Security Engineering (application security) · weight 12 · confidence high*

> The core WordPress attack surface is genuinely locked down — every $wpdb call is prepared, every state-changing path has capability+nonce, there is no IDOR anywhere, and payment verification/replay/amount-binding are real and unit-tested — but the upstream provisioning path silently discards its idempotency key while blindly retrying POSTs, and two SECURITY.md/THREAT_MODEL claims don't survive contact with the code.

The fundamentals are executed to a professional standard and I verified them individually rather than taking the docs' word: every one of the ~35 $wpdb call sites is prepared or uses constant identifiers, all 14 admin-post handlers plus the wizard carry capability-then-nonce, every phpcs:ignore EscapeOutput site resolves to HTML assembled from esc_html/esc_attr parts, the claimed UNIQUE keys exist in Schema.php, SSRF is structurally impossible (fixed hosts, rawurlencode on every dynamic segment), uploads are MIME-whitelisted with wp_check_filetype_and_ext, and the sandbox gateway fails closed via sandbox_blocked() so it cannot settle a live sale. Not 90+ because a demanding reviewer would block on the provisioning-retry and salt-provenance items; well above 75 because everything an attacker would actually reach first is correctly closed.

**What holds up**

- SQL injection is genuinely closed: I audited every `$wpdb->query/get_var/get_row/get_results/insert/update/delete` in src/ — the only string-interpolated SQL is constant table names built from `$wpdb->prefix` (e.g. `Ledger::table()`), and even the dynamic `IN (…)` list in `OrderService::claim_paid` (src/Orders/OrderService.php:174-183) is a `%s` placeholder template spread through `prepare()`. `Menu::dashboard()`'s `$demo_filter` (src/Admin/Menu.php:85) is a literal chosen by a boolean, not input.
- Object-level authorization holds by construction, not by check: no `/me/*` handler ever selects a row by a request-supplied ID. `Rest\Routes::me_list` (src/Rest/Routes.php:191-217) passes `get_current_user_id()` into `Ledger::entries`, `Services::list`, `UsageSync::customer_usage`; `Notifier::mark_read` scopes the UPDATE with `['id' => $id, 'customer_id' => $customer_id]` (src/Notifications/Notifier.php:83); and the sandbox payment page enforces `$owner !== get_current_user_id()` before minting a proof (src/Front/Shortcodes.php:191).
- CSRF/authz coverage on admin writes is complete and I verified it pairwise: all 14 `admin_post_arvrs_*` handlers route through `Actions::guard()` = `current_user_can('manage_options')` then `check_admin_referer($action, 'arvrs_nonce')` (src/Admin/Actions.php:43-49), the wizard repeats both (src/Onboarding/Wizard.php:140-143), and every form in templates/ emits `wp_nonce_field()` with an action string that matches its `name="action"` value. No `admin_post_nopriv_` alias exists for any admin action.
- Payment verification is a real cryptographic check, not theatre: `SandboxProvider::verify` recomputes `hash_hmac('sha256', ref|amount|type, wp_salt('nonce'))` and compares with `hash_equals` (src/Payments/SandboxProvider.php:39-45), the amount comes from the DB row not the request (src/Payments/PaymentService.php:58), and the claim is an atomic `UPDATE … WHERE payment_ref=%s AND amount=%d AND status IN (payable)`. `tests/unit/PaymentVerificationTest.php` actually asserts tampered-amount, cross-ref, cross-type and missing-proof all fail closed.
- The idempotency claims are backed by real DDL, which I checked: `UNIQUE KEY uniq_ref (ref_type,ref_id,type)` on the ledger, `UNIQUE KEY order_id` on services, `UNIQUE KEY payment_ref` on orders, `UNIQUE KEY uniq_period` on usage (src/Install/Schema.php:66,99,119,136) — and `Ledger::append` correctly uses `rows_affected===0` plus a `last_error` check to distinguish a benign replay from a real DB failure rather than silently dropping a credit (src/Wallet/Ledger.php:63-71).

**Findings**

- `EX-007` 🟠 high **RealProvider discards the idempotency key while ArvanClient blindly retries POSTs — duplicate billable upstream resources** — `src/Arvan/RealProvider.php:137 + src/Arvan/ArvanClient.php:64-104`  
  ArvanCloud accepts `POST /regions/{r}/servers`, the response times out at 20s or returns 502, the client re-POSTs, and a second server is created upstream. Only the first `remote_id` returned is stored in `arvrs_services`, so the duplicate is invisible to the plugin: it is never listed, never usage-synced, never deleted on cancel, and bills the reseller's Arvan account indefinitely. The three local idempotency layers in `Provisioner` cannot see it because the duplication happens below them, inside a single `create()` call. SECURITY.md's "A browser refresh, duplicated callback, or twice-delivered job cannot create two remote resources" is true as written but reads as a retry-safety guarantee the code does not provide.
- `EX-050` 🟡 medium **THREAT_MODEL S5 "DB dump alone is useless" is false on any install without salt constants in wp-config.php** — `src/Support/Crypto.php:22-26`  
  On a WordPress install where salts were not written into wp-config.php (managed hosts that auto-provision, hand-rolled installs, restored-from-migration sites), the sodium key material and the `token_enc` ciphertext live in the *same* database. A single DB dump — the exact M3 adversary the threat model names — decrypts every stored ArvanCloud API token, which grants full control of the reseller's upstream account. The plugin never checks or surfaces which case it is in; the Health page (src/Admin/Menu.php:252) reports `sodium` availability only.
- `EX-051` 🟡 medium **POST /me/topup is unrate-limited and writes a permanent wp_options row per call** — `src/Rest/Routes.php:89-99 + src/Payments/PaymentService.php:107-115`  
  Any registered customer (registration is open and self-service) can loop `POST /me/topup` and add unbounded permanent rows to `wp_options` — one per request, never garbage-collected, surviving until plugin uninstall. That is authenticated storage exhaustion plus degradation of every `get_option`/`wp_load_alloptions` path on the site, from an endpoint whose neighbours are all throttled. The intent rows also accumulate silently after every successful top-up, so even normal use leaks rows.
- `EX-052` 🟡 medium **Refund credits the wallet without confirming the original payment was ever ledgered** — `src/Admin/Actions.php:286-292 + src/Payments/PaymentService.php:75-82`  
  Because the normal payment pair nets to zero on the wallet (credit `payment` + debit `purchase`), a refund is a net `+amount` wallet credit that assumes the pair was written. If the pair was dropped by the swallowed exception (deadlock, disk-full, connection loss — exactly the conditions the catch exists for), refunding that order mints wallet credit backed by nothing, which the customer can then spend on further provisioning. The audit trail records the discrepancy but nothing blocks the action.
- `EX-053` 🟡 medium **Two SECURITY.md control claims are not true of the code (get_owned has no production callers; not every route has an args schema)** — `SECURITY.md:17,70 vs src/Services/Services.php:63 and src/Rest/Routes.php:74-77,101-107`  
  Neither gap is currently exploitable — the ownership guarantee actually comes from session-derived IDs in `me_list` and the SQL-scoped `mark_read` — but a reviewer who trusts the control inventory will believe a centralized ownership helper is enforcing single-row access. The first future endpoint that takes a service ID (a "view service" or "cancel service" route) will be written against a document that says the check is already centralized, when in fact nothing calls it. A false entry in a control inventory is a latent authorization bug.
- `EX-114` ⚪ low **Public registration silently overrides the site's membership setting and leaks account existence** — `src/Identity/Customers.php:61-85 + src/Front/FormActions.php:47-59`  
  Activating the plugin turns on open user registration on any WordPress site regardless of the admin's Membership setting — a surprising security-posture change for a site that deliberately disabled it. The differential error also gives account enumeration (slowly: 5 probes per 10 minutes per IP, trivially parallelised across IPs), and 8 characters with no complexity or breach check is a weak floor for accounts that hold spendable wallet balances.
- `EX-115` ⚪ low **arvrs_notice / arvrs_error are attacker-controlled reflected text in both admin and front notices** — `templates/admin/partials/notices.php:4-5 + src/Front/Shortcodes.php:156-157`  
  Not XSS — `esc_html` is correctly applied at every sink and I verified all of them. But an attacker can hand an admin or a customer a link like `…/wp-admin/admin.php?page=arvan-reseller-credentials&arvrs_error=<attacker text>` that renders arbitrary text inside a first-party WordPress error banner. That is a credible phishing/social-engineering primitive on a page that also hosts the API-token entry form ("Your ArvanCloud token expired — re-enter it below").
- `EX-116` ⚪ low **Test harness ships inside the plugin with no ABSPATH guard** — `tests/integration/e2e.php:1-40, tests/bootstrap.php:1-20`  
  Both files are directly requestable at `/wp-content/plugins/arvan-reseller/tests/…` on a default install. Execution fails fast (undefined classes) rather than doing damage, but with `display_errors` on it discloses the absolute filesystem path and PHP version in the fatal, and `bootstrap.php` will happily define global function shims in a web request context. It is also the one place in the codebase that breaks the otherwise uniform direct-access guard.
- `EX-117` ⚪ low **Rate limiter is a non-atomic read-modify-write, so burst limits are bypassable** — `src/Support/Helpers.php:82-91`  
  N parallel requests arriving inside one read-write window all pass, and the counter advances by 1 instead of N. The login limiter (10/600s per IP, FormActions.php:34) and the payment-callback limiter (30/300s per IP, Routes.php:156) can therefore be exceeded by a straightforward concurrent burst rather than serial requests. These are throttles rather than authorization boundaries, so impact is bounded — but the claimed protection is weaker than stated.

**Opportunities**

- Provisioning runs synchronously inside the public payment callback with blocking sleeps — `create_server` polls `for ($i = 0; $i < 5 …) { sleep(3); … }` (src/Arvan/RealProvider.php:198-203) and `ArvanClient` does `sleep(max(1, $after))` on 429 (ArvanClient.php:97). A callback can therefore occupy a PHP-FPM worker for 15-30s. The durable job is already enqueued first (PaymentService.php:91), so the inline attempt could be capped at a couple of seconds and left to the job runner beyond that.
- The admin page callbacks in `src/Admin/Menu.php` carry no `current_user_can()` of their own, relying entirely on the capability passed to `add_menu_page`/`add_submenu_page`. That is the standard WordPress idiom and is effective (the page hook is only registered when the cap passes), but a one-line `current_user_can('manage_options') || wp_die(...)` in `Menu::render()` would make the guarantee local and match the defense-in-depth posture the rest of the codebase takes.
- The audit log has no retention policy or pruning — `arvrs_audit_log` grows without bound, and `Audit::log` is called on every provisioning success, credential test and payment confirmation. A cron sweep keeping N days (with the security-relevant `level='audit'` rows kept longer than `level='error'`) would prevent the table from becoming the site's largest.
- `Audit::redact` masks by key name only (`token|api_token|password|secret|authorization|pat`), so a secret appearing in a *value* — e.g. an upstream error body echoed into `Audit::error('arvan.api_error', ['message' => substr($message, 0, 300)])` — is persisted verbatim. A regex value-scrubber for high-entropy or `Bearer`/`Apikey`-prefixed strings would close the gap the key-based approach leaves open.

### Accessibility & i18n — 66/100

*Accessibility & Internationalization · weight 5 · confidence high*

> The customer-facing storefront shows genuine, above-average accessibility craft — associated labels, correct tab/alert ARIA, bidi-aware `dir="ltr"` on every LTR data field, reduced-motion support — but the admin UI has no label association at all, the shared color tokens fail WCAG AA in both stylesheets, and the "i18n" is `__()`-wrapping without an actual catalog, a `lang` attribute, or locale-switchable direction.

The storefront half earns real credit: 100% label association with correct autocomplete, four `aria-label`ed navs, `aria-current="page"`, a properly wired tablist/tabpanel set kept in sync by JS, differentiated `role="alert"` vs `role="status"`, focusable opacity-0 radios with `:focus-visible` rings, a genuine reduced-motion block, ~15 deliberate `dir="ltr"` bidi overrides, and a single clean text domain across 619 call sites — that is upper-70s work in isolation. It loses points to three material, provable defects: zero label association across ~40 admin fields (contradicting the readiness doc's explicit claim), a shared token palette where four of five status pills and the admin primary button fail AA by computed ratio, and an i18n layer that is `__()`-wrapped but has no .pot, no `languages/` directory, no `lang` attribute, and a hardcoded `dir="rtl"` that makes translation cosmetic. Focus loss on payment success and reveal-based live regions cost the async flow further. Competent with weaknesses a reviewer would insist on fixing — 66.

**What holds up**

- Front-end form controls are 100% label-associated with matching `for`/`id` and correct autocomplete tokens — `templates/front/auth.php:36-41` (`for="arvrs-login-email"` + `autocomplete="email"`, `autocomplete="current-password"`, `new-password` on register), `templates/front/product.php:73-92` (region/image/name/domain/bucket), `templates/front/dashboard.php:167-168` (top-up amount).
- Serious bidi discipline that most RTL projects skip: `dir="ltr"` is applied to roughly fifteen LTR-content fields and cells — API tokens (`templates/admin/wizard.php:42,87`), emails/phones, payment ref (`templates/front/payment.php:39`), plan IDs and connection strings (`templates/front/dashboard.php:99,121,128`), the usage period range (`dashboard.php:213`). Combined with `inputmode="url"` and real `pattern` attributes on domain/bucket (`product.php:84,91`).
- Tab ARIA is wired correctly and kept in sync by JS: `templates/front/auth.php:20-21` gives `role="tablist"`, `role="tab"`, `aria-selected`, `aria-controls`; the panels carry `role="tabpanel"` + `aria-labelledby` (`auth.php:31,46`); `assets/js/front.js:27-33` updates `aria-selected` on both tabs and toggles `hidden` on both panels. Dashboard navigation uses real links with `aria-current="page"` (`dashboard.php:66`).
- Live-region semantics are differentiated rather than blanket: `role="alert"` for errors (`product.php:110`, `dashboard.php:170`, `auth.php:26`), `role="status"` for non-urgent async updates (`payment.php:50` progress, `payment.php:65` replay result, `auth.php:29` notice). Decorative content is hidden — `aria-hidden="true"` on the spinner, hero shapes, plan dot, breadcrumb chevron, and all inline SVG icons.
- The visually-hidden plan radios stay keyboard-operable: `assets/css/front.css` uses `.arvrs-plan-card input { position:absolute; opacity:0; width:0; height:0 }` (not `display:none`) and pairs it with `.arvrs-plan-card input:focus-visible + .arvrs-plan-body { outline: 2px solid var(--arvrs-brand); outline-offset: 2px }` — the correct pattern. A real `@media (prefers-reduced-motion: reduce)` block ends the file, killing the float animation and slowing the spinner. Text domain is perfectly consistent: 619 occurrences of `'arvan-reseller'` and no second domain.

  A screen-reader user in wp-admin hears "edit, blank" for the brand name, support email, API token, markup percentage, warning threshold, negative-credit cap and spending limit. Roughly forty controls that configure pricing, credit policy and ArvanCloud credentials are unidentifiable without sighted context, and clicking the label text does not focus the field. This directly falsifies HACKATHON_READINESS.md:25, which claims "labels on every field ✅".
- `EX-048` 🟠 high **Shared status-tag palette fails WCAG AA in both stylesheets — success pill is 2.89:1** — `assets/css/front.css (.arvrs-tag-* block), assets/css/admin.css:60-66`

- `EX-109` 🟡 medium **Customer-facing ArvanCloud error messages bypass `__()` entirely** — `src/Arvan/DTO.php:88-96`

Together with the three hardcoded Persian strings in `assets/js/front.js`, an English or Arabic translation of the plugin would still show Persian at exactly the moments the user most needs to understand what happened.

The admin button is a regression against a WordPress default that already passed.

Live regions whose content changes while unrendered, or that are merely un-hidden, are announced inconsistently across NVDA/JAWS/VoiceOver, so the "در حال تأیید پرداخت…" and error messages may never be spoken. The failure branch uses a raw `alert()` (front.js:109), a blocking modal with no styling or context.

  A reseller picking any light or mid teal/yellow/lime — which a bare color picker invites — silently drops the primary CTA, the wallet chip, the active nav link and every focus ring below AA, with no warning in the UI. The derived ramp (`brand-2`, `brand-3`, `brand-ink` via `color-mix`) is well-designed but only safe for dark inputs; the failure is ungated rather than inherent.
- `EX-140` ⚪ low **`role="tablist"` has no arrow-key navigation, and admin focus ring is downgraded to a failing 1px** — `assets/js/front.js:25-35, assets/css/admin.css:87`

- `EX-141` ⚪ low **Shortcode output nests `<main>` inside the theme's `<main>` and adds a second `<h1>`** — `templates/front/partials/shell-top.php:47, src/Install/PageFactory.php:41, src/Front/Shortcodes.php:27-33`

The result is two `main` landmarks (invalid HTML, ambiguous "skip to main" target) and two `<h1>`s per page, so heading-based navigation lands on the theme's page title rather than the plugin's real page heading. Every amount, count, order ID and timestamp is therefore Persian-numeraled regardless of locale, even though `'تومان'` itself is wrapped in `__()`. Routing through `number_format_i18n()` and gating the digit map on the active locale would make the numeric layer as translatable as the string layer.
- Provider catalogs carry untranslated Persian product data — `src/Arvan/RealProvider.php:72-74` (`' هسته'`, `' مگابایت'`, spec key `'دیسک'`), `:83-85` (`'پایه'`, `'رشد'`, `'حرفه‌ای'`), `:98` (`'۱۰۰ گیگابایت'`), `:130-131` (region names), plus `DemoProvider.php:35-56`. ### Integration honesty — 66/100

*Third-Party Integration Correctness & Claim Honesty · weight 6 · confidence high*

> The integration boundary is well-architected and unusually honest at the documentation level (explicit NOT-AVAILABLE table, forced demo mode until a credential passes a live test, `is_demo` revenue isolation, correct GPL/OFL claims), but real mode carries several provable defects that demo mode completely hides — non-idempotent POST retries, a cloud-server catalog that cannot price itself in real mode, unvalidated config forwarded upstream after payment, and zero test coverage of `ArvanClient`/`RealProvider`.

The design of the boundary earns real points: one interface, normalized `ProviderError` with correlation IDs and a customer-safe message split, bounded retries with `Retry-After` handling, demo mode that is forced until a credential genuinely authenticates, `is_demo` revenue isolation, and licensing claims that verify exactly. Points come off for defects that only bite in real mode and that the demo provider structurally hides: method-agnostic retry of non-idempotent creates with no upstream idempotency, a cloud-server catalog whose base costs are keyed to demo-only plan IDs, unvalidated region/image forwarded upstream after payment, and an inline provisioning path that can strand a paid order in an unrecoverable state. Add zero test coverage of `ArvanClient`/`RealProvider` and three doc claims (402 handling, 5 s connect timeout, redacted request logging) that the code does not implement, and this lands as competent-with-material-weaknesses rather than strong.

**What holds up**

- Error normalization is real and complete: `ArvanClient::handle()` (ArvanClient.php:113-133) maps every upstream status to a `ProviderError{kind}` with an 8-char correlation ID, and `ProviderError::customer_message()` (DTO.php:87-97) keeps upstream bodies away from customers while the internal message keeps the detail — the split is actually enforced, not just documented.
- Demo/real boundary is honest by construction: `Plugin::demo_mode()` (Plugin.php:49-57) forces demo until `Credentials::has_verified_credential()` returns true (a credential that actually passed a live `test_connection`), orders carry `is_demo` (OrderService.php:~110), and `Admin\Menu.php:85` excludes demo orders from revenue/margin in real mode. A judge cannot accidentally be shown simulated revenue as real.
- `docs/API_INTEGRATION.md:52-61` is a genuinely useful limitation table, and the code matches it: `RealProvider::usage()` (RealProvider.php:317-320) returns `[]` with a comment naming itself as the single future integration point, and `BaseCosts` exists precisely because no pricing API does.
- Licensing/legal claims check out: `assets/fonts/*.woff2` are genuine WOFF2 files, `assets/fonts/OFL.txt` is the real SIL OFL 1.1 with the Vazirmatn copyright line, `LICENSE` is GPL-2.0, and the plugin header (`arvan-reseller.php:9`) and README both say GPL-2.0-or-later. No overclaim.
- `Payments/SandboxProvider.php:41-46` is honestly labelled a sandbox and still performs a real server-side check — `hash_hmac` over `ref|amount|type` keyed by `wp_salt('nonce')`, compared with `hash_equals` — so amount/ref tampering fails exactly as a real PSP would, rather than a fake always-OK stub.

**Findings**

- `EX-006` 🔴 critical **ArvanClient retries non-idempotent POSTs on timeout/5xx, defeating the documented single-invocation guarantee** — `src/Arvan/ArvanClient.php:64-104`  
  A response timeout on `POST /regions/{region}/servers` (cURL 28 after Arvan already accepted the create) causes a second and third identical create. The customer is billed for one server; the reseller's upstream account is billed for up to three, and only one `remote_id` is ever recorded — the orphans are invisible to the plugin and can only be found in the Arvan panel. The same applies to `POST /domains/dns-service` and `POST /buckets`. DemoProvider makes this unreachable in demo (`DemoProvider::create` is a local `update_option`, no HTTP, no retry), so the failure mode cannot surface in any demo or test.
- `EX-042` 🟠 high **Real-mode cloud-server plans are keyed by upstream flavor IDs, but BaseCosts is seeded only with demo plan IDs — the headline product is unsellable in real mode** — `src/Pricing/BaseCosts.php:59-63 vs src/Arvan/RealProvider.php:67-75`  
  The moment an operator switches to real mode, every cloud-server plan whose upstream ID is not literally `g1-1-1-25`-style disappears from the storefront; the product page renders an empty plan list and the storefront card shows `from = null`. CDN and Object Storage survive only because RealProvider hardcodes the same IDs the seed uses. This is exactly the drift the demo hides, and it is not listed in the README's "Known limitations" — which says base costs are "seeded from the public pricing page" without noting the seeded keys only match the demo catalog.
- `EX-043` 🟠 high **Inline provisioning with up to 15 s of sleep() in the payment callback can strand an order in `provisioning` with a live upstream resource** — `src/Payments/PaymentService.php:91-97, src/Arvan/RealProvider.php:199-218, src/Provisioning/Provisioner.php:44-46`  
  If PHP's max_execution_time (commonly 30 s) kills the request after `POST /servers` succeeded but before `Services::create_for_order`, the order is permanently stuck in `provisioning`: the queued job returns "not claimable", which `JobRunner::execute` (JobRunner.php:113-116) explicitly treats as job success, and the admin's `retry_provision` action (Admin/Actions.php:268-271) routes through the same unclaimable path. Result: customer paid, server exists and bills upstream, no service row, no admin recovery short of SQL. DemoProvider returns instantly with no network and no sleep, so neither the e2e script nor any demo can reach this state.
- `EX-044` 🟠 high **Customer-supplied region/image are never validated against the offered catalog, and flavor IDs are region-scoped** — `src/Orders/OrderService.php:36-39 vs src/Arvan/RealProvider.php:64, 153`  
  A customer can legitimately select a region other than the one the flavor list came from, pay, and only then have `POST /regions/{B}/servers` rejected because `flavor_id` belongs to region A — landing in `provision_failed` after money changed hands. A forged/mangled `image` id does the same. ## What happens to these findings

The point of an audit is the work it causes. Every finding carries a stable ID, an owning dimension, a severity and an effort estimate in [the backlog](review/ISSUE_BACKLOG.md), and is intended to be worked in this order:

1. **Critical first**, regardless of effort — these either lose money, mislead the user, or misrepresent the product.
2. **Then the convergence list above**, because multiple independent reviewers pricing the same file is a strong prior that something is genuinely wrong there.
3. **Then high-severity items by weight of dimension** — a high finding in Security (weight 12) outranks a high finding in Accessibility (weight 5).
4. Items that will not be fixed get marked `accepted-risk` **with the reason written down**, not quietly dropped. An audit that is allowed to shrink by deletion is not an audit.

Findings are not closed by disagreement. Closing one requires either a commit that changes the behaviour, or a new fact — a command output or a code line — that shows the reviewer was working from a wrong premise.

## How this record was produced

1. Fifteen reviewer agents were launched in parallel, each with one dimension, the scoring scale, and the instruction to read source before scoring.
2. Each returned a structured result: score, confidence, one-sentence verdict, rationale, strengths, and findings with severity / location / evidence / impact / recommendation / effort.
3. Their raw structured output was rendered into this page and the backlog by a generator script — no reviewer's score or wording was edited on the way in.
4. The weighted total is a plain weighted mean of the dimension scores using the weights in the table above.

Reproducing it requires re-running the panel; the value of the record is that the reasoning behind every number is written down next to the number.
